# XPAN 可恢复要求与交付门槛

用户明确要求“可恢复”。此要求适用于后续菜单、显示、拍摄参数及运行时代码改动。**最小诊断指针的立即恢复已在相机上验证；完整 XPAN 恢复流程尚未验证，现有模块不是可安装文件。** 当前没有将 XPAN 代码部署到相机；固件版本未改。具体机身结果见本文末尾。

## 当前实现的回退能力

| 层级 | 实现 | 验证范围 |
| --- | --- | --- |
| XPAN 状态 | 保留用户原画面比例，退出后投影回普通设置 | 电脑端三种裁切×四种普通比例及第五项 XPAN 检查通过；未绑定相机属性 |
| DNG 分派 | `gr4_xpan_dng_disable()` 关闭覆盖，保留原函数委托 | 电脑端验证重复关闭后仍调用原函数；不等于已卸载机内挂钩 |
| DNG 参数块 | 修改前记录原字段；恢复前核对所有字段仍为本模块的修改值 | 电脑端逐字节恢复通过，保留其他字段 |
| 422 源描述 | 记录原像素地址与宽高，可恢复到原源图范围 | 电脑端逐字节恢复通过；只处理描述，不恢复已编码照片 |
| XPAN 机内代码/菜单/图标 | 尚无模块安装器、原生同步或完整恢复入口 | 未验证；阻止部署 |

`firmware/xpan_undo.c` 提供两个带原值记录的缓冲适配入口及统一恢复函数。恢复需要原缓冲仍有效，并持有相机原生锁。它检查目标地址、长度及全部被修改字段；如果其他流程已改变这些字段，拒绝恢复且不写任何字节。活动记录不能被新的修改覆盖。恢复成功后重复调用是无操作。

`gr4_xpan_dng_disable()` 必须先于原生挂钩卸载。关闭覆盖后仍需让原函数及模块内存保持有效，直到所有挂钩恢复、指令缓存同步并确认没有调用仍在模块内执行。这个函数本身不安装或移除挂钩，也不证明模块可卸载。

`firmware/xpan_hook_txn.c` 新增最多 16 个四字节挂钩位点的事务核心。安装前核对所有原值，写入后逐项回读并调用外部发布回调；失败则逆序恢复并再次发布。卸载前要求所有位点仍为本模块替换值；恢复不确定时状态置为 2，不调用外部解锁回调，避免恢复不完整时继续执行。故障注入测试覆盖原值冲突、部分写入、发布失败及回退失败。**它仍未提供机身上的任务暂停、跨核缓存发布和独立恢复执行器；目标位点也未经过完整实机核实，故不能部署。**

## 当前 SD 运行方案的边界

### 2026-10-02：挂钩回滚失败后可重试的事务核心

新增 `gr4_xpan_hook_recover_original()`，保存已经持有的暂停回调与 context；恢复不重复加锁，只在所有原值、发布和再核对成功后解锁。卸载预检失败现在也保持暂停，不放行可能混合的挂钩集合。13 组主机故障检查与统一模块 ARM 编译通过，包括恢复失败后再试、未知值不覆盖、错误拥有者拒绝及不重复解锁。

这不替代实机任务排空/缓存/独立恢复适配器；代码和记录必须在未确认恢复时继续保留，当前没有完整 XPAN 安装/卸载包。详见 [预览与恢复研究记录](research/2026-10-02-preview-and-hook-recovery.md)。

1. 功能代码、菜单分派及显示改动计划限定在 RAM。安装器要逐项列出地址、长度、原内容、替换内容及核对依据；不能只保存一个升级包当作运行时回退备份。
2. XPAN 自有持久状态如需要保存在 SD 卡独立文件中。相机原生属性设置可能触发自动保存，相关路径仍要核对；必须防止 XPAN 覆盖原用户设置后写进内部持久存储。
3. 每次开机重新确认机型、版本及关键原始字节。无法匹配时停止加载。不得沿用上次开机的堆指针。
4. 安装前读取并保存全部待改内容。安装中任何一步失败，都必须恢复已改部分并逐项回读；恢复不完整时，不得把混合状态报告为可用，也不得释放仍被引用的模块内存。
5. 热卸载须在停止新拍摄、结束已有拍摄并确认模块调用退出后进行。顺序为关闭 XPAN 覆盖、恢复挂钩/菜单/显示及用户设置、同步缓存、回读核对，最后释放模块。上述原生操作尚未实现。
6. 相机异常时，外部禁用加载入口不能依赖 XPAN 菜单或模块还能运行。SD 启动入口可从电脑禁用；移除含加载器的卡后冷启动恢复原厂是设计目标，**仍需机身实测，不能现在保证“拔卡重启即可恢复”**。

升级包刷写不属于当前已验证的恢复路径。官方升级文件及其离线重建结果不能证明相机故障后还能进入升级界面，也不能证明可以降级。若重新采用刷写方案，必须先独立验证可用的原厂恢复入口。

## 部署前必须完成的机身验证

- 明确原生 RAM 装载、任务同步、缓存同步和完整卸载方式。
- 对最小临时改动完成“读原值→修改→回读→恢复→回读”，之后再验证无加载器的冷启动。
- 在部分安装失败和运行中停用时恢复全部已改项；正常模式仍可预览、拍摄和回放。
- 相机原裁切、比例及内部持久设置保持一致；普通重启与外部禁用入口均能回到原厂功能。
- 回退入口与 XPAN 功能分开，恢复材料同时保存在电脑和 SD 卡，不能只有机内模块持有原值。

电脑端关闭覆盖、参数恢复与最小诊断控制流检查通过；实机已验证一次 4 字节诊断指针的立即恢复。原生 XPAN 挂钩、无加载入口冷启动及故障恢复没有完成，因此不部署 XPAN 机内补丁。

## 电脑端复核

```sh
python3 tools/check_xpan_core.py /private/tmp/xpan-reversible.arm.o
```

输出路径必须不存在。检查覆盖原选项恢复、同张照片窗口、像素源行选择、原字段恢复、错误目标、短缓冲、并发改值冲突、重复恢复及 DNG 原函数回退；同时编译 ARMv7/VFPv3 硬浮点对象并拒绝未解析符号。它不执行相机代码，不验证机内代码恢复，也不修改已保存照片。


## 最小诊断指针恢复测试（2026-09-30）

本轮不安装 XPAN。`tools/build_sd_recovery_probe.py` 默认生成只读脚本；显式 `--arm-ram-probe` 才允许一次临时 4 字节 RAM 写入。目标仅为工程命令表中 `SYS_buildinfo` 的处理函数指针，不改指令、资源、拍摄设置或版本。

每次执行先从 `0x553A094C` 重新读取本次开机的命令表地址，要求 651 条、四字节对齐、完整表位于已用地址保护范围内。逐字节核对读取、写入、原诊断函数、短复制路径、原生返回函数及三条命令记录，并保存原指针。比对包括 NUL 和完整文件长度；任一条件不符即停止写入。

临时目标 `0x538C9760` 是固件已有的 `MOV r0,#3; BX lr`，不分配或执行新代码。写入前建立 `XRTRY.TXT`，防止再次执行写入测试。核心事务连续执行“替换指针→调用诊断→恢复原指针”，每条命令后立即保存返回值，恢复尝试之前没有 SD 操作、等待或分支。然后回读原指针、调用原函数并比对五字节画面比例/裁切属性。

第二次正常开机仍插着同一张卡，仅重新解析当前指针并只读核对；不是无加载入口冷启动测试。日志中有第二阶段并不足以证明实际经过关机，需用户确认两次正常开关机。独立 `script/recovery.ttl` 接受的待恢复值只有原指针和上述确定的原生函数指针，遇到未知值不覆盖。该独立入口需要电脑明确选择，尚未在机身上运行。

电脑端控制流检查通过：默认只读、立即恢复、新开机地址解析、重复执行保护、八种前置故障阻止写入、两种写后故障仍尝试恢复，以及恢复失败后的独立入口。它们是合成检查，不是机身实测。参考固件字节保存在忽略目录及用户卡上，不在仓库分发。

已部署包位于本地 `devkit-output/xpan-recovery-probe-20260930-v2/`：八个 `.REF` 文件及两个脚本，全部独占新建；启动脚本最后写入，十个文件逐字节回读匹配。原入口字节及上一轮结果哈希匹配，所有新结果名部署前不存在。部署清单记录于同目录 `deployment.json`，SD 卡已安全弹出。

用户操作：相机关机插卡，正常开机等待 90 秒，正常关机至完全熄灭；不拔卡再正常开机等待 90 秒，关机后将卡接回电脑。如出现异常，停止继续测试并接回电脑读取记录。读取时先备份，再核对并移除启动入口。`tools/analyze_sd_recovery_readback.py` 仅分析电脑副本，分别判断临时恢复、第二阶段检查和用户确认的正常重启；不将这些结果解释为 XPAN 已可安装或模块卸载已验证。


### 第一轮实际结果：前置比较未通过，未进行指针修改

2026-09-30 用户完成操作并接回卡后，已备份并逐字节核对 21 个文件到 `devkit-output/xpan-readbacks/2026-09-30-recovery-1/`。第一阶段日志完整结束，但 `all checks passed=0`、原命令结果保持初始化值 `-999`，未到达地址记录或事务准备步骤；`XRTRY.TXT` 不存在。因此没有执行本轮 RAM 写入，不能报告恢复成功。第二阶段日志不存在：此前置失败未生成阶段推进标记，后续开机看到原日志即停止，不能据此判断用户是否进行第二次开机。

五段代码、三条命令记录在电脑上精确匹配参考；命令表地址 `0x591F1480`、数量 651、对齐和地址范围均有效，原 `SYS_buildinfo` 指针为 `0x53054854`。差异集中在机内 TTL 比较或文件处理过程，其具体原因尚未确定；不跳过这个保护条件。核对原包及电脑副本后已移除第一轮启动脚本，保留记录和独立恢复文件。

新增 `tools/build_sd_binary_compare_probe.py`：只读九组合并诊断，包括四组 SD 控制（相同的含 NUL 数据、内容不符、短文件、多余字节）和五组原代码比较。逐组记录比较结果、位置、字符代码和读/EOF 返回值。脚本不含 `SYS_reg` 或其他内存写命令；电脑端控制结果与失败位置检查通过，尚待实际 TTL 核对。六个文件已新建并逐字节核对，SD 已安全弹出。只需一次开机等待 90 秒后正常关机并回读。


### 比较故障已定位，长度核验修正版已部署

2026-09-30 第二轮只读诊断完整读回，12 文件备份核对于 `devkit-output/xpan-readbacks/2026-09-30-binary-compare-1/`；旧启动脚本核对移除。九组记录中，正常相同控制数据逐字节比较到最后一字节，五段代码也比较至末尾，电脑核对全部精确匹配。内容不符控制在索引 1 读到 2 与 1，正常识别差异。但所有末尾读取都仍返回 0；短文件索引 3 甚至读到不属于文件内容的 167。原保护条件据此把正常文件误判为有尾部。不能从 EOF 读取返回值或读取字节判断文件长度。

这与 [Tera Term 官方 `fileread` 文档](https://teratermproject.github.io/manual/5/en/macro/command/fileread.html) 规定的 EOF=1 不同。今后以本机记录为准。新方案使用 [`filestat`](https://teratermproject.github.io/manual/4/en/macro/command/filestat.html)；已静态核对本机 token、分派、原生状态适配及整数长度输出路径，同时新增两段原代码参考用于机内比对。电脑模型改为实测 EOF=0 并可能返回残留字节，不再沿用标准 EOF 假设。

修正版每次先用四组含 NUL 的独立控制数据，验证文件长度 4/4/3/5、比较应为真/假/假/假，缺失控制或异常长度也会停止。正式比较前后都检查准确长度，只读取边界内的字节；单字节整数解码也先检查偏移小于实际长度。十三种前置故障、两种写后故障、立即恢复、新开机重新解析地址及独立恢复入口的电脑检查通过，所有检查没有越过 EOF 读取。此结果不代表机身已验证恢复。

新包 `devkit-output/xpan-recovery-probe-20260930-v3/` 使用 `ZP` 输出前缀，避免覆盖第一次的 `XR` 记录。十个原代码/命令参考、五个长度控制文件及两个脚本共 17 项全部在卡上核对；复用匹配的旧参考，独立恢复脚本先完整写入临时文件再替换已备份原版，启动入口最后启用，SD 安全弹出成功。唯一可能的修改仍为 `SYS_buildinfo` 的临时四字节 RAM 指针，不改新指令、设置、内部文件或版本，也不安装 XPAN。前置控制和原字节核对均通过才会执行；第一次立即恢复，第二次仅只读检查。用户仍需两次正常开机各等 90 秒，中间不拔卡。后续回读分析须指定 `--output-prefix ZP`。
