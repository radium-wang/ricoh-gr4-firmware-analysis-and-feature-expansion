# GR IV Camera Mode / Debug：消费者追踪

日期：2026-09-30。方法：本地固件 ARM 静态分析；本轮未改动相机、SD 卡或固件。

分析对象：`samples/gr4_decoded.bin`（不随仓库分发），SHA-256：
`c4e597c7c9ca1bc181b30e35139ed90a4fd876ddcca14f12be0e00b6702233ae`。

## 结论

已从工厂菜单设置追到实际读取该模式的界面代码。已证实的用途包括：

1. 保存 Debug 模式，下一次启动加载；启动日志输出 `=== DEBUG MODE ===`。
2. 一个界面显示 `Camera Mode: Normal/Debug`。
3. 版本信息入口页面在 Normal 下显示两段版本号，在 Debug 下显示四段版本号。
4. 同一入口页面在 Debug 下有条件地开启限时按键序列识别；匹配后可跳转到 `DevelopmentMenuController`。

第 2—4 项为静态代码结论，尚无对应实机截图。不能从这些结果推导出提高拍摄性能或自动开启 USB 终端、Script、Serial Input。也不能宣称整个固件绝无其他间接消费者。

## 地址映射：避免把运行时表读错

RTOS 的文件起点为 `0x17D10`，代码虚拟基址为 `0x53000000`。代码/只读数据的文件位置为：

```text
file_offset = virtual_address - 0x53000000 + 0x17D10
```

但可写数据另有启动搬运。`0x5300038C` 开始的代码将 `0x5437B640` 的 `0x57480` 字节复制到 `0x55000000`。因此 `0x55018EF8` 的函数表不能按代码基址直接换算；其 ROM 来源是 `0x54394538`，文件位置是 `0x13AC248`。

## 设置到公共属性的完整链路

| 环节 | 地址/字段 | 核对结果 |
| --- | --- | --- |
| 工厂菜单设置 | `0x5337DAD8` | 枚举 5=Normal，6=Debug；CameraModeData `+4` 写 `0xFFFFFFFF` / `0x5AA5A55A`，并调用保存路径 |
| 菜单运行时更新 | `0x53750DC0` | group=0、property ID=`0x0E`、一字节布尔值 |
| 启动加载 | `0x53A79BC0` | 读取保存的 `+4`，Debug 分支输出启动日志，再调用下面的同步更新 |
| 启动运行时更新 | `0x53758EC0` | group=1、property ID=`0x0E`、一字节布尔值 |
| 公共属性接收 | `0x5375AD68` | group=0/1 分别进入异步/同步设置处理；对象名为 `ComPropIf` |
| 属性表第 14 项 | RAM `0x55018F68`；文件 `0x13AC2B8` | 指向 `0x5374C07C` |
| 属性写入 | `0x5374C07C` → `0x5375E064` | 写公共属性数据的 `+0x5F` 和影子区 `+0x8A7`，随后交换/同步属性缓冲 |
| 属性读取 | `0x53755AC4` → `0x5375C2C8` | 加锁读取公共属性 `+0x5F` |

这条路径属于公共属性管理器。早期“发送到控制系统”的描述过于宽泛，不能据此认定是 SystemControl 的硬件模式切换命令。

## 消费者 1：模式文字

`0x531B7004` 的界面更新函数在 `0x531B7090` 调用 Debug getter：

- 关闭时选用 `Normal`；
- 开启时选用 `Debug`；
- 同一块代码使用标题 `Camera Mode:`。

这些字符串分别位于 `0x53F9EDB4`、`0x53B4A57C`、`0x53D79CFC`。显示仍受该界面自身的可见性条件控制，不能描述成在所有拍摄画面叠加 Debug 标签。

## 消费者 2：完整版本号

`0x531B7FC8` 构造的类由 RTTI 确认为 `FactoryEntranceController`；它的页面使用 `Version` 标题。启动分派 `0x5325CEF8` 用消息 `+4` 的**开机代码 4** 记录 `Startup : Version`（字符串 `0x53D7B72C`）。该分支把页面模型状态置为 2，第二次分派才在 `0x5325D038` 发出页面 ID `0x0100000E`，并由控制器工厂入口 `0x53185F7C` 内的 `0x5318679C` 分支构造 `FactoryEntranceController`。此前把页面模型状态 2 误写成开机代码 2，现已纠正。它不是普通设置的“相机信息”，也不是关机总结画面。构造时在 `0x531B8040` 读取 Debug，并缓存到对象 `+0x170`。

`0x531B80CC` 起按该值选择格式：

| 模式 | 格式字符串 | 提取方式 |
| --- | --- | --- |
| Normal | `%02d.%02d` | 32 位版本值的最高两个字节 |
| Debug | `%02d.%02d.%02d.%02d` | 同一个 32 位值从高到低的全部四个字节 |

格式字符串位于 `0x53D79F90` 和 `0x53D79F7C`。例如假设内存版本值是 `0x010B0A00`，这两种显示分别是 `01.11` 和 `01.11.10.00`；这是说明字节格式的假设例子，不是本机版本读回。

此处证明的是**显示格式**。升级器怎样比较版本仍需独立分析，不能从格式推断降级/升级规则。

## 消费者 3：版本入口页的隐藏按键路径

`0x531B7EFC` 开始的页面进入路径：

- 检查一个初始化为 1 的全局字节 `0x55001E8C`。
- 将缓存的 Debug 状态复制到对象 `+0x178`，作为序列识别是否启用的标志。
- Debug 为真时，调用定时器，参数为 `0x1388`（十进制 5000）。尚未独立核实这里的时间单位，所以不把“5 秒”写成实测事实。
- 随后清零全局字节。按这一条初始化/访问路径，它只在本次启动的首次进入时尝试开启；Normal 下先进入也会消耗这个机会。
- `0x531B7DA8` 的超时回调清零识别标志。

`0x531B823C` 处理有效按键事件，凑齐四个内部事件号后比较两组序列：

| 序列（内部十进制 ID） | GR IV 机身按键 | 常量地址 | 跳转 ID |
| --- | --- | --- |
| 29, 29, 4, 5 | 回放 → 回放 → DISP → MENU | `0x53D9ECC4` | `0x01000008` |
| 10, 11, 27, 5 | 下 → 左 → Fn/删除 → MENU | `0x53D9EBC4` | `0x0100000B` |

`0x531B8334` 起发送跳转；控制器工厂中，两种跳转经 `0x5318757C` 使用构造函数 `0x531B84E8`，其 RTTI 为 `DevelopmentMenuController`。

按键对应关系来自 `0x53271FF8` 对键盘表的初始化：ID 4=`Disp`（`0x53D7BB54`）、5=`Menu`（`0x53D7C67C`）、10=`Down`（`0x53D8DD60`）、11=`Left`（`0x53D8DD38`）、27=`Fn`（`0x53D8DD28`）、29=`Play`（`0x53D79D98`）。`0x532719C8` 筛选按下事件，序列不是同时按住四个键，而是在限时窗口内依次按下。理光官方 [GR IV 机身按键图](https://www.ricoh-imaging.co.jp/english/products/gr-4/spec/parts.html) 确认 DISP、MENU、回放、下、左、Fn/删除按钮的位置。

用户已实测：Debug 开启后，普通“相机信息”和关机画面仍没有四段版本号；将官网固件放在 SD 卡并按 MENU 开机也没有进入这个 Version 页面；取出 SD 卡再按 MENU 开机则正常启动。该结果推翻了此前把 MENU+电源、无卡启动与 Version 页面相连的建议。理光官方说明，MENU+电源配合 SD 卡根目录中的 `fwdc248b.bin` 是固件更新入口，预期页面是“Update the camera firmware”，不是这里反汇编出的 `Startup : Version` 页面（[官方更新步骤](https://www.ricoh-imaging.co.jp/english/support/digital/gr4_s.html)）。

### 开机代码 4 的来源与实机验证

这条路径现已追到物理按键，不再只凭 `Startup : Version` 字符串猜测：

1. `0x538D42D4` 把开关 ID `0x21600221` 装入开关监控表第 9 项（从 0 计数），位置为对象 `+0x80`；前端按键表 `0x5327261C` 对同一 ID 标注 `RDIAL Push`（字符串 `0x53D7BC10`）。理光官方的[机身部件图](https://www.ricoh-imaging.co.jp/english/products/gr-4/spec/parts.html)把该物理部件称为 `ADJ./Rear e-dial`。这里指**按下后拨轮/ADJ.**，不是旋转后拨轮或按中央 OK。
2. `0x538D4900` 逐个读取开关监控表；开关对象的虚方法 `0x538D5E8C` 分别给出开关 ID 和按下状态，调用方从输出的第二个字段取按下状态，将第 9 项复制到开机开关快照的字节 `+9`。消息 `0x21600326` 将该快照指针传给系统控制器；`0x53A906EC` 保存到对象 `+0xB8`。这避免把 `RDIAL Push` 的 ID 低字节误当成按下状态。
3. `0x53A7AE80` 在启动原因值为 1 时调用 `0x53A8C844`。后者只在快照字节 `+9 == 1` 时返回真；为真则选开机代码 4，否则选代码 1。开机代码 1 在接收端记录 `Startup : Playback`，因此**不能把原因值 1 直接解释为按电源键开机**；它更可能是回放键开机的一类路径。`0x53A7C1AC`、`0x53A7B240` 和消息 `0x26409E06` 将代码送往应用；`0x532595DC → 0x53259734 → 0x5325CEE8` 接收并选择 `Startup : Version` 分支。

**实机已验证：**Camera Mode 保持 Debug、相机关机后按住机背右上角 ADJ./后拨轮的按压动作，再用**回放键**开机；用户确认出现标题为 `Version` 的页面，且显示**四段版本号**。无需更新固件或更改工厂菜单中的其他项目。先前提出的“后拨轮＋电源键”漏看了相邻 `Playback` 分支，已撤回。用户随后文字报告该页显示 `01.11.10.07`，与本地官方 1.11 升级包头四字节一致。

这是 Debug 开关控制的另一个工程菜单入口。两组按键虽然最终都由 `DevelopmentMenuController` 处理，尚未实测各自打开的具体分类。它们只是在 Version 页已显示且识别窗口启用后才被读取，不能用来从普通开机画面调出 Version 页。

## 覆盖范围

在代码区的 ARM B/BL 扫描中，公共 getter `0x53755AC4` 的直接调用点是 `0x531B7090` 和 `0x531B8040`；底层 getter `0x5375C2C8` 的直接调用点是 `0x53755AF0`。按完整函数指针字节查找，也未找到这两个 getter 的数据表指针。

这支持上述两个界面消费者的定位，但并不覆盖一切可能的结构整体复制、经别名访问、内联、跨处理器传输或其他固件版本。其他对象中同为 `+0x5F` 的字段不能因偏移相同就归为 Debug。

同一启动函数分别处理日志、Serial Input、卡门等独立配置。设置 Camera Mode 的路径没有同时改写它们；本次追踪也没有建立 Debug 到 CPU 时钟、内存容量、录像分辨率或 USB 接口配置的因果路径。
