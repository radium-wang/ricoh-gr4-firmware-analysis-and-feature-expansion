# 2026-10-02：原厂预览坐标、比例提示与挂钩失败恢复

本轮先完成电脑代码和检查，随后用户连接 GR IV，执行一组合并 USB 只读查询。相机会话已关闭，未写相机 RAM/SD 或安装挂钩。**XPAN 尚未安装；本轮没有完整预览/图标适配器或安装器。** 原厂 JPEG/DNG 候选代码及上一轮实机记录继续保留。

## 先补明确的恢复缺口

`firmware/xpan_hook_txn.c/.h` 原事务在回滚失败时保留 state=2 和暂停状态，但没有公开的重试恢复入口；卸载前的原值核对失败还会解锁，这可能放行一个混合挂钩集合。

本轮新增 `gr4_xpan_hook_recover_original()`：

- 暂停成功后保存回调副本和 context；state=2 保持 guard，代码、记录和 context 必须继续有效。
- 重试须使用同一组回调和 context，直接利用已经持有的 guard，不再次 enter，避免锁重入。
- 逆序检查和恢复；只处理原值或本模块替换值，未知第三方值不覆盖。部分恢复仍保留暂停。
- 所有原值回读、外部 publish 和再次全量核对均成功，才返回 state=0 并 leave 一次。
- 卸载预检发现冲突或读失败时，也进入 state=2，不放行调用者。
- 拒绝损坏的位点记录、错误恢复 context/回调、活动期间重复安装或普通卸载。调用者须串行执行，不可重置活动记录。

13 组主机故障检查覆盖：重复地址、正常安装卸载、安装预检冲突、提交后写失败、发布失败、回滚失败留锁、错误恢复拥有者、重试不重入/重复解锁、enter 失败、卸载第三方冲突、读失败、恢复写/发布失败后重试、损坏记录。结果位于 `hook-recovery-host-v2/checks.json`；旧 v1 也保留。统一 portable 模块主机检查与 ARM hard-float 编译通过，无未解析 ARM 符号。

**边界：** enter/read/write/publish/leave 是注入的主机服务，未验证实机图像 worker 排空、跨核发布或独立 USB 恢复执行器。这补全了事务核心的失败重试，并不等于完整 XPAN 可热卸载。状态 2 时不得释放模块代码；若执行恢复的线程也被暂停，须由独立入口处理，目前该原生绑定尚未实现。

## 原厂画幅提示不能接收任意图标指针

固定样本 SHA-256 为 `c4e597c7c9ca1bc181b30e35139ed90a4fd876ddcca14f12be0e00b6702233ae`。`audit_gr4_preview_native.py` 核对完整样本、局部代码哈希、名称、直接调用及倍率常量。

`0x53216260`（`UpdateGuideChangeAspect`）由原 UI 刷新 `0x53216C2C` 调用，取 controller `+0x170` 画幅提示 widget。controller ID `0x0400003F` 才更新；`0x04000040/41` 隐藏。原属性 `+0x18` 的 0..3 分别选择资源 `0xF1/0x15B/0xF0/0x15D`，底资源为 `0x1DB`；5 隐藏，**4 进入原厂断言**。因此不能直接把第五项的内部值 4 发给这个原函数。

`0x53577BDC` 设置 widget 的模式/两个资源子项并更新可见性，调用 `0x53576E38`。后者比较并保存子项 `+0xEA` 的 **16 位资源编号**，再失效重绘；不读取文字指针、SVG 或位图。项目现有 XPAN SVG 只是电脑参考图，未成为相机资源。本轮执行到真实资源编号存储，布局/失效/可见性服务模拟，不证明屏幕已经画出了图标。

## 预览 VirtualWindow 不等于已找到 LCD 裁切

LiveViewProcess `+0x3A0` 指向 `LiveViewInformation`（主虚表 `0x53FD1830`）。上一轮只读实机关系可支持对象定位，不能复用其地址作为下次开机的安装地址。

`0x538876B8`（原字符串拼写 `UpdataCropVirtualWindow`）锁定信息对象 `+0x24E8`，按模式/比例/整数倍率写入 `+0x24..0x40` 的两组宽高与中心原点，再解锁。原调用点包括：

| 调用点 | 参数来源 |
| --- | --- |
| `0x5362E4D4` | crop float × **8192.0**，加 0.5 转无符号整数；mode=0 |
| `0x53637E78` | LiveViewProcess `+0x91/+0x8D/+0x94`，信息对象来自 `+0x3A0` |

在后一个入口附近还更新其他 recipe/坐标状态。信息对象 mutex 的存在不能证明显示任务/3A/AF 全部已排空。非零 mode 会进入原断言。比例分支包含内部 4/5，但这不表示菜单第五项 XPAN；界面提示函数恰好拒绝 4。

逻辑满幅常量为 `0x2D0000/0x1E0000`。它们虽在数值上等于 720/480 × 4096，**本轮没有确定所有相关字段的单位，更没有确定是 LCD 像素窗口**。方形分支的第二组宽度使用字面量 400 的专门计算，不能用统一比例映射假定所有模式。`GetLiveViewDisplayResolutionRemote` 支持 720×480→mode `0x1E`、1080×720→`0x1D`，这也不足以确认当前 LCD viewport。

`0x53887474` 是另一条加锁信息发布路径：把输入 `+4/+8/+C/+10` 复制到自身 `+0x7C..+0x88`，调用 `0x5377AB54` 并更新状态。本轮未给它提供 XPAN 参数，也未证明它直接控制显示裁切。`BlackMaskImageCoordinator` 的名字出现在图像处理/黑电平上下文，不能仅凭名称当成 LCD 黑边入口。

## 27 组真实原 ARM 检查

`check_gr4_preview_native.py` 的最新结果 `preview-native-arm-v9/checks.json`：

- 18 组：OFF/35/50 倍率 × 原函数的六个内部比例分支，执行原厂整数除法和坐标存储，核对中心原点及锁/解锁调用。倍率位值为原代码使用的 `0x3F800000/0x3FA04F89/0x3FE23119`，换算为 8192/10260/14476。
- 1 组：非零模式到断言即停止，不模拟“断言后正常运行”。
- 6 组：UI 比例 0..3 的真实资源字段、4 的断言、5 的隐藏。
- 2 组：两种其他 controller 模式隐藏提示。

对象、两组坐标基准及 crop 状态为模型；mutex、属性查询、布局/重绘/可见性服务为模拟。没有 pixel buffer、显示硬件、AF、拍摄或 encoder 验证，不设置 PREVIEW_READY/ICON_READY。

失败记录全部保留：v1 沙箱缺宿主缓存信息；v2/v3 缺原 64 位除法代码页（v3 增加 PC 诊断）；v4/v5 混用模型坐标/像素基准；v6/v7 漏掉方形分支的 400 特例。v8 首次 27 项通过，但 50mm 模型倍率手填 14477；v9 改从原 IEEE 位值和 8192 常量计算为 14476，再次通过。这些均是电脑检查问题，没有相机写入；未把失败当成功或删除。

### 用户接 USB 后实际完成

用户确认开机连接后，相机 `25FB:2123 / bcdDevice 0111` 重新枚举。第一次把释放 `ptpcamerad` 与占用接口分为两个进程，接口 claim 返回 Access denied，未发送 PTP 命令。改成预加载依赖、仅终止当前用户的精确 `/usr/libexec/ptpcamerad`、在同一进程立即运行查询后成功；失败也保存，不当成相机通信故障或参数读取结果。

`capture-preview-information-live-v1.json` 中的新对象为 LiveViewProcess `0x59CBA498`、LiveViewInformation `0x59A550E0`，没有复用上轮地址。`+4/+8` 基准与 `+14/+18` 均为 `2949120/1966080`，`+0x1CD4` 除数为 **4096**；两个满幅窗口也都是 W/H=`720×4096 / 480×4096`、X/Y=0。这个读数支持该路径使用 4096 比例坐标，但不单独证明实际 LCD 像素、显示黑边或 AF 变换。

发布字段 `+0x7C/+0x80/+0x84/+0x88` 为 `196608/196608/1376256/884736`，除以 4096 是 `[48,48,336,216]`，其实际消费者/语义仍待追踪，不当成 LCD 画幅。JPEG 配置仍为空，源宽/高/pitch 为零；USB 状态没有可用拍摄帧。前后原回调/scratch/拍摄属性及注册表身份一致，会话已关闭，没有申请或保留相机 RAM。

用实测基准追加 18 组离线原 ARM 分支检查，最新 `preview-native-arm-v10/checks.json` 共 **45 项通过**，仍模拟服务、不接像素硬件。这里的方形分支第二窗口宽度使用 400 的基准映射，不能认为两组窗口永远等同；此前使用 divisor=1 的模型没有代表这一真实单位。

### 共享拍摄计划的双窗口坐标代码

新增 `firmware/xpan_preview_coordinates.c/.h`，并纳入 portable unity build。输入是既有 JPEG/DNG 捕获计划及原厂两个 W/H/X/Y 窗口，要求 aspect=0、倍率 8192/10260/14476 与计划 crop 位值匹配。保留原窗口横向裁切和原点，分别把计划实际对齐后的 photo.top 与 photo.bottom 映射到两组窗口，先计算边界再相减，避免另外算近似 65:24 导致不同范围。

它验证计划、两个坐标域/窗口边界，全部计算成功后才写输出，支持输入输出同址。采用有界整数长除法处理超过 32 位的乘积，不依赖浮点近似或未绑定的 ARM runtime；失败不改原窗口或输出。**它不修改原信息对象，不安装调用点，不发布 LCD/AF 参数；PREVIEW_READY 仍为 false。** 原窗口必须由原生调用者在正确 crop/所有权/锁下提供，计算接口本身无法证明这些条件。

`preview-plan-coordinates-arm-v3/checks.json` **35 项通过**：使用原 ARM 在实测 USB 坐标基准上的三种 crop/aspect=0 窗口，套用与 JPEG/DNG 相同的测试计划；三种 crop 各核对独立输出/同址；大乘积和非零原点；14 类错误各核对独立输出/同址时不写。像素来源和 `[1,4,2]` 对齐仍为模型，不能认定为真实 AF/显示或图像编码验证。

构建 v1 拒绝未解析 `__aeabi_llsr`：变量 64 位右移被编译器生成为 runtime 调用。改用两组 32 位移位提取乘积位；v2 的 21 项通过，v3 增加同址失败原子性为 35 项。失败/两个成功版本全部保留。最终统一模块主机检查及 ARM 编译无未解析符号。
