# GR IV 热靴联动关机与从关机启动附件的可能性

2026-10-13。固定样本为 `samples/gr4_decoded.bin`，内部版本 `1.11.10.7`，SHA-256 `c4e597c7c9ca1bc181b30e35139ed90a4fd876ddcca14f12be0e00b6702233ae`。机身代码结论来自静态分析，没有修改固件。用户运行的 v3/v4 SD 脚本已确认 GF-2 的 C1=`11 00`，以及 A6 关闭后的完整测试结果。

**v4 实测更新：用户确认 A6 `01 00` 后灯自行关闭；三次主动 C0，以及另一组 A6 `01 02` 后的 C0，均只读到 `00`，灯没有自行打开。** 11 个阶段完整执行，正常检测恢复命令均返回 0。它排除了本次条件下这两种已测序列的启动效果，不能排除所有软件唤醒方式，不能据 `00` 确定灯主控断电。见[v4 完整结果](2026-10-13-gr4-hotshoe-a6-test-v4.md)。

之后 v5 用户仍观察到没有自动开启，并明确确认手动开灯后的图标和关机联动都正常。v5 卡上日志尚未读回，不能填入其 RX 值或宣称阶段全部执行。结合 v4 的完整取证，当前已测 C0/A6 软件开灯方案可判为不可用，无需继续重复相同序列；尚无依据断言 GF-2 在硬件上绝对不能被其他信号唤醒。详见[v5 观察与结论](2026-10-13-gr4-hotshoe-manual-power-v5.md)。

**新发现：机身关机准备步骤明确发布 A6 参数 `01 00`，正常默认参数为 `01 02`。这为联动关机提供了直接的机身端代码依据；仍未证明 GF-2 的关机电路、两个参数字节的完整含义，或远程开机能力。** 可绕过普通附件识别的参数化收发测试函数，已在 SHELLCMD 文本注册表中找到命令名称。用户随后上机执行了缓冲入口的单次 C0 查询，回复 A5；这确认了无需外置单片机或修改程序代码的原厂通路。

## 为什么联动关机不等于联动开机

灯工作时可以接收参数，收到关机相关参数后关闭主要功能。关机后是否仍有电路监测热靴、以及哪种信号能够恢复工作，是另一项硬件和灯端软件能力。

“关机”可能指主控休眠、部分电路断电，或主要控制电路完全停机。机身固件无法独自确定 GF-2 属于哪一种，也不能从“灯已灭、指示灯已灭”判定收发电路是否仍工作。自动关机和用户按键关机还可能进入不同状态。

官方 GR IV 手册第 70 页要求先打开机身，再打开 GF-2。[官方手册](https://www.ricoh-imaging.co.jp/resources/english/support/man-pdf/gr-4_en.pdf) DPReview 的原始 GR IV 评测也明确描述 GF-2 随机身关机，但不随机身开机。[原始评测的附件部分](https://www.dpreview.com/reviews/ricoh-gr-iv-in-depth-review/) 这些支持正常使用行为，不提供灯内电路原理，也不能证明定制信号无法启动它。

## 新追踪到的关机参数链

```text
关机计划加入步骤 0x601
        ↓
SHUT_DOWN_STEP_PREPARE_SHUT_DOWN_START
        ↓
发布附件请求 15，参数 0x0100
        ↓
AccessoryArbitrate：写入 A6 参数，选择 CameraState 18
        ↓
HotshoeControl：重新检测附件、检查模式 1 / 协议 0x10
        ↓
发送命令 A6，两个 payload 为 01 00
```

| 证据位置 | 确认的行为 |
| --- | --- |
| `0x53660B88 → 0x53660B8C` | 关机计划构造时加入步骤 `0x601` |
| `0x53663A64…0x53663A78` | 步骤 `0x601` 映射到字符串 `SHUT_DOWN_STEP_PREPARE_SHUT_DOWN_START`，字符串位于 `0x53EB3A90` |
| `0x53EB25B4` | 虚表指向步骤事件处理函数 `0x5365C6BC` |
| `0x5365C6F0…0x5365C7F4` | 处理 `0x601`，调用 `0x5365B8F4` |
| `0x5365B954…0x5365B980` | 请求参数 `+0x0C=0x0100`，附件请求类型 `15`，送入 `0x5377008C` 的消息队列 |
| `0x53770D40…0x537713A0` | 请求 15 进入 A6 参数发布路径，以状态 `18` 输出 |
| `0x53772890…0x53772898` | 高字节保存到 Manager `+0x72`，低字节到 `+0x73` |
| `0x53A736E4…0x53A7371C` | 状态 18 读取上述两个字节，使用 A6 descriptor 发送 |

因此，`A6 01 00` 是**关机准备路径构造并要求发送的帧**；不是本轮抓到的线上帧。检测失败时输出分支会退出，机身代码也不验证 A 系列回复作为附件确认。

正常默认参数 `0x0102` 来自既有 AE 初始化/参数构造；缺省参数回退也使用它。`01 00` 与 `01 02` 的差别，很符合“关机时缩短等待”的解释，但还不能把首字节定义成开关标志、第二字节定义成秒，更不能认定 `01 02` 是开机命令。灯端代码或波形才能确认是否立即关闭、延时关闭、睡眠或关闭充电电路。

## 从关机启动：哪些路径还有探索价值

### 1. 普通 A 系列输出受到识别门控

`0x53A73660` 先调用附件检测。检测先读取 HotSdai 和 AD，只有串行模式才尝试 C0/C1。发送 A6 等参数还要求模式为 1、协议状态为 `0x10`。

若关机灯不呈现有效的电气识别条件，或者不回复 C0 的 A5，正常路径不能把 A6 当作“先发一个命令叫醒灯”。这是机身软件的门槛，不是灯硬件不可唤醒的证明。实际关机 GF-2 的 AD/数据线状态尚未测量。

### 2. HotCtl / HotCtlEn 的证据不支持直接称为电源开关

初始化 `0x53A729C0` 按 ProjectType 和另一个运行时硬件分档绑定 GPIO。具体条件：

- ProjectType 2、分档 0：跳过 HotCtl 与 HotCtlEn。
- ProjectType 2、分档 1：绑定 HotCtl，跳过 HotCtlEn。
- ProjectType 2、分档大于 1：两者均绑定。
- 其他被支持的 ProjectType 亦经过相关分支。

硬件分档 getter 位于 `0x538E7FC0`，读取 RAM 字节 `0x553A0854`，其设置与板版本数据有关；本轮没有实机值，不能替用户的 GR IV 选定某个分支。

在当前 HotshoeControl 代码区间 `0x53A729C0…0x53A738D0`，两个 GPIO 对象字段 `+0x10/+0x14` 的实际读取用于初始化设置，未发现后续开机脉冲流程。其他相同偏移出现在命令表和构造清零中，不能误算为 GPIO 切换。这个局部扫描不排除其他组件直接操作同一硬件端口。

### 3. 通信开启和关闭会改变信号，可作为待测唤醒来源

`OpenCommunication(1)` 使片选、时钟、输出线经过初始化设置，并开启 SIO；`CloseCommunication` 关闭 SIO、把片选/时钟/输出线设置为逻辑 0。收发时片选先为逻辑 0，传完为 1。这些电平变化可能被灯端监测，但目前没有证明 GF-2 将某条线或某个边沿设为开机来源。

HotshoeControl 虚表 `0x543540F0` 中的若干生命周期槽只指向立即返回的函数；不能把对象生命周期初始化当作隐藏的灯电源启动。

### 4. 找到绕过普通检测的收发测试代码

`0x530603CC` 接收数字参数，构造命令/payload descriptor，随后：

```text
CloseCommunication
OpenCommunication(1)
Transfer(指定 descriptor、发送缓冲、接收缓冲)
CloseCommunication
```

函数体没有调用 `CheckAccessoryAttachment`，所以代码上可以在未建立 kind/协议状态时发出帧。另一缓冲测试函数 `0x5306060C` 也调用传输例程。

已核对目标传输函数的 16 条直接 ARM BL 调用：正常 C0/C1/C2–C5、扩展 50、A 系列，以及上述两个测试调用。没有从这些调用定位到固定的“开机命令”。命令名称和注册入口见下面补查；静态调用扫描本身没有访问设备，后续用户执行的单次查询另列为实机证据。

**这一路径已在 v4 实测：绕过普通检测，A6 关闭后发送 C0，未恢复 A5 或完整开机。** 即使返回 A5，也要区分“收发电路醒了”与“灯完整开机、充电并可发光”；收发函数返回或缓存 C9 不能代替物理波形。

## 无外置硬件、无固件修改：原厂工程命令入口

补查解码文件内 `SHELLCMD`：头部在文件偏移 `0x02E89810`，正文 41,664 字节，共 651 项。注册记录为**文本中的十六进制地址**，不是 ARM 的直接 BL，也不是四字节函数指针；此前只按后两种形式追踪，所以漏掉了这个入口。

| 表索引（从 0 计数） | 原厂命令名 | 处理函数 | 文本记录的解码文件偏移 |
| --- | --- | --- | --- |
| 626 | `HotshoeCheckDisable` | `0x53060358` | `0x02E934A0` |
| 627 | `ExeHotshoeCommType1` | `0x530603CC` | `0x02E934E0` |
| 628 | `HotshoeCommType1` | `0x5306060C` | `0x02E93520` |
| 629 | `HotshoeGetHotDetAd` | `0x53060794` | `0x02E93560` |

原厂 SD 脚本 `sendln` 经 `0x538EF3C8` 进入工程 shell `0x538EEFF4`，匹配命令名后调用注册处理函数，处理函数返回值写入脚本 `result`。该通路此前已有[基础诊断的实机证据](../2026-10-01-gr4-usb-factory-path.md)。2026-10-13 新实机日志确认 `HotshoeCheckDisable` 和 `HotshoeCommType1` 的暂停、发送、读回复、恢复通路；`ExeHotshoeCommType1` 和 `HotshoeGetHotDetAd` 尚未执行。[脚本通路审计](../../tools/audit_sd_shell_path.py)

`ExeHotshoeCommType1` 参数为 `命令号 显示方向 数据字节数 [发送字节…]`。显示方向只影响本函数日志打印，实际收发仍是全双工。数字通过 `0x53155F8C` 以 **base 10** 解析，因此 C0 必须写成十进制 192：

```text
ExeHotshoeCommType1 192 0 1
```

没有提供发送字节时，局部 TX 缓冲为零；这条命令构成 C0 + 一个 00 占位数据字节，打印接收到的字节。它不先检查 A5、kind 或协议状态。处理函数返回 0 仅表示控制流走完，不能当作附件回复。

为了让 SD 脚本记录回复，可使用有持久 RX 缓冲的另一入口：

```text
HotshoeCommType1 0 0 0       # TX[0] = 00；只设置机内测试缓冲
HotshoeCommType1 1 192 1     # 发送一次 C0 / 1 字节数据，关闭通信
HotshoeCommType1 2 0         # 读取 RX[0]，作为函数返回值
```

这里的注释仅作说明，不应把该文本块整体输入机身。实际脚本形式为 `sendln '命令及参数'`。RX 缓冲在 RAM `0x553A310C`，TX 在 `0x553A3210`；不用通过 SetData 写这些地址，原厂命令自己管理缓冲。脚本读取 RX[0] 后，165 对应 A5；201 对应 C9，但 C9 也可能是真实数据，不能仅凭数值确认超时。

已准备[单次 C0 查询脚本](../../examples/probe-gr4-hotshoe-c0.ttl.example)：以正常检测已启用、相机空闲为前提，临时暂停检测，设置一个零占位字节，发送一次 C0，读取回复，恢复检测后再记录日志。它只在 SD 卡写 `C:\HSC0.TXT`；已有该文件时退出，防止每次启动重复发送。创建日志失败或找不到已创建的文件时，在发送前退出；恢复检测先于后续文件操作，避免日志打开失败跳过恢复。没有发送 A0/A6、未知 opcode，也没有注入代码或改写函数表；原厂命令会自然改变通信状态和测试缓冲。

按现有 Script 功能运行时，需要在卡上使用 `script/startup.ttl` 并启用 Script；已有启动脚本应先备份，不能叠加运行。查询前新增 15 秒等待，让正常开启时的基线测试有时间手动打开 GF-2；关闭状态实验不要在等待期间按灯的电源键。其扩展名 TTL 指机内脚本语言，不是闪光测光协议。

用户连接 SD 卡后，已核对 `GR-SD` 为外置可移除 FAT32 `/dev/diskNsM`。旧 XPAN 启动脚本、恢复副本和实验记录共 11 个文件（25,786 字节）先完整备份并核对，随后清理旧实验文件和空目录。部署的三个文件已逐字节读回核对，新 `startup.ttl` 为 2,665 字节，SHA-256 `561c1a92edd79f70392c98058ae51dda7506cb6a10b41ab786a19025996ba7bd`。macOS 随主日志移除了 AppleDouble 旁文件；检查后完成剩余清理。电脑记录在 `devkit-output/gr4-hotshoe-c0-test-20261013-v1/`。没有发送相机命令，也没有修改相机设置。具体操作见[单次查询测试说明](2026-10-13-gr4-hotshoe-c0-test.md)。

首次实验应先在灯开启时确认脚本能记录 A5，再对用户按键关机、机身联动关机后的灯分别测试。暂停检测与等待并不构成排他的硬件锁，所以实验期间不能同时拍摄、半按或运行其他热靴测试。若异常中止、恢复未完成，需停止脚本并重新启动相机，不能把脚本正常结束路径当作异常恢复保证。

**现在已由用户运行的 SD 日志确认主动 C0 查询得到 A5；尚不能确认“查询能够从关机启动 GF-2”。** 机身由用户运行，电脑只读取取回的 SD 日志，没有直接热靴波形或本轮运行时命令表回读。USB RunFunc 是另一个按类别/编号分派的接口，尚未建立它与这四个 shell 命令的直接对应，不能把命令字符串当成 USB RunFunc 参数。

第一轮 `HSC0.TXT` 共 365 字节，暂停、准备、发送、恢复四项均返回 0，RX 为 165，包含完整结束行。原始日志及结构化解析保存于 `devkit-output/gr4-hotshoe-power-batch-20261013-v2/card-backup/HSC0.TXT` 和 `first-round-result.json`。随后用户运行了[连续测试 v2](2026-10-13-gr4-hotshoe-power-batch-test.md)，但 `HSB2.TXT` 只有 168 字节的开头三行，没有测量、恢复或完成记录；即使等满 180 秒也出现联动缺失。执行位置、原因和 A6 是否实际发送均未确定，因此仍没有有效 C1 或唤醒测量。v2 已撤下，改为[先恢复检测、逐条记录的 v3](2026-10-13-gr4-hotshoe-recovery-v3.md)。

后续 v3 已完整执行：`HSC3.TXT` 为 689 字节，六次查询和恢复均返回 0，C1=`11 00`，C2=`01 00`，C3/C4=`00 00`，C5=`1A`。用户确认正常图标和关机联动恢复；现在已有本次 GF-2 对应 kind 0x11 的实机依据。详见[实机回复记录](2026-10-13-gr4-hotshoe-live-readings.md)。之后 v4 已完整执行，A6 关闭后的已测序列没有自动启动，结果见本文开头及[A6 参数逐帧记录 v4](2026-10-13-gr4-hotshoe-a6-test-v4.md)。此前 v2 的日志仍不能用于判断 A6 或唤醒效果。

## 下一次实测如何区分可能性

优先使用上面的原厂脚本观察回复和灯的实际行为，不需要制作外置硬件。每次实验应保存上一轮日志，再删除卡上的 `HSC0.TXT`，才会执行下一次查询；已有启动脚本应先备份：

1. 灯正常开启：先确认这四个命令在实机可用，单次查询是否记录 A5。
2. 机身关机导致灯关闭后：先观察普通机身重开的行为，再运行单次查询，记录回复及灯是否恢复指示、充电和闪光能力。
3. 用户按键关闭灯后：重复单次查询，与联动关机状态比较。
4. 如回复和实际行为不能解释，再使用热靴测量接口核对波形、AD 和 A6 payload；这属于后续取证，并非调用原厂命令的必要条件。

| 结果 | 对启动能力的意义 |
| --- | --- |
| 普通机身重开无 C0，强制 C0 后完整恢复 | 支持机身门控/未发送唤醒序列的限制；可继续研究软件或转换器触发 |
| 自动关机可恢复，按键关机不可恢复 | 支持灯存在不同关闭状态 |
| 回复 C0 但不充电/不能主闪 | 收发电路恢复，不足以宣布完整开机 |
| 无回复、无恢复 | 只说明已测序列无效；不能证明所有热靴启动方式都不可能 |

若主要收发和唤醒电路都断电，普通串行命令无法被执行，需要额外硬件启动路径。GF-2 是否具备这种断电结构，目前没有其内部固件或电路证据。自制附件可以自行设计常供电的低功耗监听电路；这不能推广为原装 GF-2 已支持远程启动。

## 离线复核

新增[电源路径审计脚本](../../tools/audit_gr4_hotshoe_power.py)，当前 v2 在已有 51 个指纹窗口之外核对 12 个窗口、11 条分支、传输函数的 16 个直接调用，另核对 SHELLCMD 全文哈希、四个注册记录及十进制参数解析入口：

```sh
python3 tools/audit_gr4_hotshoe_power.py samples/gr4_decoded.bin \
  --output /tmp/gr4-hotshoe-power.json
```

输出必须不存在。记录的关机帧为静态推导；标注不代表自动反编译出的灯端语义。直接 ARM BL 扫描不能排除间接调用或 Thumb 调用。本轮审计已通过，并确认修改或截断后的样本会被拒绝。

查询示例另用主机上的流程模型检查了 11 种情况，包括 A5/C9/零回复、已有日志跳过、各命令失败和恢复后日志丢失；临时暂停检测期间没有文件操作，已进入热靴流程的结束路径均会尝试恢复检测。模型不能保证恢复命令成功或异常断电时恢复，也不验证相机脚本解释器、ARM 执行、电平或灯端行为。审计与模型本身没有执行固件；用户运行的单次查询结果见上述新增实机记录。
