# GR IV 机内 XPAN 画面比例：固件定位与实现条件

## 目标

在拍摄菜单中提供 XPAN 选项；选择后，实时取景按 **65:24** 构图，拍摄文件按同一取景范围保存，拍摄界面显示相应图标。模式切换和重启后的状态也需要一致。

用户要求可恢复；这是实机部署的必要条件。原始内容备份、独立回退入口、故障回退及无加载器的冷启动恢复必须先验证。现有电脑端模块已增加关闭覆盖和缓冲字段恢复，但机内恢复流程未验证；详见[恢复要求与验证状态](xpan-recovery.md)。

XPAN 的比例来自哈苏公布的 24×65 mm 全景画幅：[Hasselblad XPan 历史页面](https://www.hasselblad.com/about/history/xpan/)。GR IV 机身最大 3:2 静态图尺寸为 6192×4128；固定全宽时，65:24 比例对应约 6192×2286 的中心裁切。实际输出尺寸须按相机图像处理器的对齐要求确定，不能仅由比例计算决定。

## 已确认的现状

理光[官方规格](https://www.ricoh-imaging.co.jp/english/products/gr-4/spec/)列出的拍摄裁切为 OFF、35mm、50mm，静态图比例为 3:2、4:3、1:1、16:9；没有 65:24。

在本地 GR IV 1.11.10.7 解包载荷 `samples/gr4_decoded.bin` 中，以下字符串可复核（十六进制数为**文件偏移**，不是运行地址）：

| 文件偏移 | 字符串 | 指向的功能线索 |
| --- | --- | --- |
| `0xDD12A8` / `0xDD1238` | `ChangeCrop` / `ChangeAspectRatio` | 裁切倍率和画面比例为两个设置路径 |
| `0xDD5490` | `GetCropModeIcon` | 裁切状态有独立的界面图标路径 |
| `0xEB6DBC` | `35mm`，随后为 `50mm`、`3:2`、`4:3`、`16:9`、`1:1` | 固件中存在这些短标签；仅凭字符串位置不能确定具体菜单资源 |
| `0xEC634C` | `LvChangeCrop` | 实时取景有裁切更新路径 |
| `0xECC748` | `CropMag 0:1.0 1:1.25 2:1.76...` 与 `AspectRatio 0:3_2 1:4_3 2:16_9 3:1_1` | 两组参数分别枚举 |
| `0xFE62AC` | `m_ImageMapParamCrop_35mm != NULL`，随后为 50mm | 图像处理还有按裁切模式区分的参数 |
| `0xFE70E8` | `SetupDngTagCropWindow` | DNG 元数据可能需要同步调整 |

复核命令：

```sh
strings -a -t x samples/gr4_decoded.bin | rg 'ChangeCrop|ChangeAspectRatio|GetCropModeIcon|LvChangeCrop|CropMag|AspectRatio 0:|m_ImageMapParamCrop_|SetupDngTagCropWindow'
```

这些字符串只能证明相关代码或数据存在，不能证明函数调用关系、资源格式、可扩展枚举范围，或修改后的固件可以被相机接受。本仓库没有 GR IV 拍摄菜单、实时取景、JPEG/DNG 管线的可编译源码，也没有经过验证的自定义固件打包、安装和恢复流程。

### 已反汇编的限制

在这一份载荷中，RTOS 段文件偏移 `0x17D10` 对应装载地址 `0x53000000`。据此可定位以下代码：

- `ChangeAspectRatio` 的调用点在 `0x5325ADFC` 附近，读取 `0x53DBB034` 的现有四项顺序表并分支。该表当前为 `00 01 03 02`；不能把追加一个字节视为完整实现。
- 四项轮换函数 `0x5325AE58` 只比较表中索引 0–3；遇到未匹配的比例 ID 时，`0x5325AE60` 反而令后续代码读取索引 **5**。因此直接给第五档分配新 ID 会读到现有表外数据。状态文字函数 `0x534DF824` 也只允许 ID 0–3；其余值进入默认分支。这两处均已加入只读审计。
- `FocusModel.cpp` 的布局路径在 `0x5339E990`、`0x5339E9B8` 两次对比例 ID 作 `<=3` 检查。早期将它称为一般显示布局，现已由错误消息的源文件身份修正为对焦模型路径；尚不能证明它控制整幅实时图像的视口。两处已加入审计；XPAN 使用独立菜单逻辑第五项，进入原生消费者时投影为合法 3:2 比例 ID 0。
- `ChangeCrop` 的调用点在 `0x5325AECC` 附近，读取 `0x53DBAC10` 的三个浮点倍率 `1.0`、`1.252427`、`1.767123`；`0x5325AF00` 将循环次数设为 3。它控制的是水平和垂直方向一起收窄的等效焦距裁切。XPAN 要保留原有水平视角、只裁上下，因此需要独立的比例路径。
- `GetCropModeIcon` 对应的选择函数在 `0x53398380`。它比较现有倍率并返回固定的图标 ID，例如 `0x1D3`、`0x63`、`0x2F`；没有对新比例直接返回图标的分支。
- Makernote 比例元数据写入函数从 `0x5380D1D0` 开始，源文件为 `ImageContents/Writer/src/PentaxMakernoteEntryDataSetter.cpp`。`0x5380D1EC` 为 `cmp r3, #3`，后面是四项跳转表；有效枚举最终交给 `0x537E7134` 按字节存储。该函数没有裁切 JPEG 像素，不能作为实际成片裁切入口。其它比例消费者仍未穷举。

用只读审计脚本复核这一固件版本：

```sh
python3 tools/audit_xpan_paths.py samples/gr4_decoded.bin
```

作为画面定义的离线参考，`tools/xpan_reference.js` 对输入图片中心裁切至最接近 65:24 的整数像素范围，同时输出上下遮罩和 XPAN 占位图标的预览 PNG：

```sh
node tools/xpan_reference.js input.jpg /tmp/xpan-example
# 生成 /tmp/xpan-example.jpg 和 /tmp/xpan-example.preview.png
```

此工具只处理电脑上的图片，不是相机固件实现。以 720×480 输入测试时，输出为 720×266，预览与 JPEG 使用同一中心范围。机内最终像素尺寸还要考虑 Bayer 起点、缩放器和 JPEG 编码的对齐要求。

## 完整实现需要核实的部分

1. **菜单与状态**：XPAN 枚举、文字、选择顺序、状态保存、重启恢复及与现有 35mm/50mm 和画面比例的组合规则。
2. **实时取景**：65:24 中心取景框、上下遮罩、方向变化，以及测光、自动对焦框和触屏坐标的映射。
3. **成片**：JPEG 输出尺寸和实际像素范围；DNG 的裁切窗口、预览图和元数据；RAW+JPEG 的一致性及机内回放。
4. **图标**：资源格式、索引、显示位置及菜单/拍摄/回放界面的调用路径。若使用 XPAN 名称或品牌图形，发布前还需核实使用许可。
5. **固件交付**：修改后包的完整性校验、机型及版本检查、相机是否接受更新、失败恢复方式，并在离线检查通过后进行受控实机验证。

## 实机确认的尺寸计算器与保留原选项的修改依据

2026-09-30 的一次开机批量 SD 读取确认 10 处裁切/显示代码及常量与同版本样本完全一致，当前比例 ID 为 0、倍率为 1.0。尺寸计算对象在本次开机读回的函数表地址是 `0x53FD89A0`，其内容与原样本一致。关键方法：

| 方法表偏移 | 地址 | 实际职责 |
| --- | --- | --- |
| `+8` | `0x538CFBF8` | 图像尺寸；`r1=分辨率/尺寸索引`，`r2=比例 ID`，`s0=裁切倍率` |
| `+0x30` | `0x538CFB5C` | 将浮点裁切倍率分类为匹配的尺寸索引，供 DNG 使用 |
| `+0x34` | `0x538CFB90` | 将尺寸索引转为对应裁切倍率 |

`tools/audit_runtime_image_calculator.py` 核对样本 SHA 与读回函数表后，读取现有四个跳转表，只解码尺寸分支中的 ARM 立即数及半字写入指令；不执行相机函数。倍率 1.0 下，各尺寸索引的分支如下：

| 比例 | 尺寸索引 0（L） | 索引 1（M） | 索引 2（S） | 索引 3（X） |
| --- | --- | --- | --- | --- |
| 3:2 | 6192×4128 | 4944×3296 | 3504×2336 | 1920×1280 |
| 4:3 | 5504×4128 | 4400×3296 | 3120×2336 | 1920×1440 |
| 16:9 | 6192×3480 | 4944×2784 | 3504×1968 | 1920×1080 |
| 1:1 | 4128×4128 | 3296×3296 | 2336×2336 | 1280×1280 |

尺寸索引 3 的分支存在，不证明用户菜单有第四种焦距裁切。JPEG 调用从拍摄参数 `+0x7E0` 读入尺寸索引；DNG 则由倍率分类得到匹配索引。早期把 `r1` 称为裁切模式，现依据这两处调用修正。这里解码的是原样本实际被机身选择的计算方法，不是拍摄文件验证；不同输出分辨率仍需分别接入。

DNG 存在不同参数类：Kb588 的 `0x5387B024` 使用基础起点 `[68,40]`；Kb636 的 `0x5387E108` 使用 `[54,58]`。两者源文件身份和加法指令均已核对。当前实机尺寸计算器属于 Kb636，但图像参数对象的运行时函数表没有读回，不能据此断言活动 DNG 参数类。

Kb636 DNG 函数先按倍率分类并计算当前窗口，再以索引 0、比例 0、倍率 1.0 计算未裁切的基础尺寸，共调用尺寸方法 `+8` 两次。因此全局把尺寸方法改为 XPAN 会同时改变基础尺寸参照，破坏居中差值；应在具体拍摄上下文中分别处理输出窗口与完整 RAW 数据范围。6192 全宽候选为 6192×2286、顶部 921，或 6192×2288、顶部 920。Bayer 起点与处理器对齐要求未验证，均不是已验证可拍摄的参数。

## 当前交互目标：画面比例第五项

用户最新纠正：裁切菜单仍为 `OFF / 35mm / 50mm` 三档；画面比例菜单保留原有四项顺序，在末尾加入 `XPAN`。固件原始顺序表 `0x53DBB034` 为 ID `[0,1,3,2]`，对应 `3:2 / 4:3 / 1:1 / 16:9`；项目第五项仅为菜单逻辑 ID 4，不能直接写入原生画面比例属性，因为原厂轮换、状态文字、对焦布局和 Makernote 路径只处理 0–3。

主菜单描述表 `0x53D9F714` 以 `0x5C` 为行跨度。画面比例是零起算第 5 项 `0x53D9F8E0`，裁切是第 19 项 `0x53D9FDE8`。本地哈希固定的 [`audit_aspect_menu.py`](../tools/audit_aspect_menu.py) 核对画面比例菜单四个回调和三档裁切保持不变：

| 画面比例槽 | 当前函数 | 现有行为与第五项所需适配 |
| --- | --- | --- |
| `+0x18` | `0x531BE2EC` | 用四字节顺序表生成标签；XPAN 需要独立标签 |
| `+0x20` | `0x531BB250` | 用原生比例 ID 判断选中项；XPAN 需要独立状态 |
| `+0x28` | `0x531BAF70` | 从顺序表取 ID 并调用原生属性设置；第五项不能越界读取或把 4 交给原函数 |
| `+0x30` | `0x531BA14C` | 返回原选项数 4；须配套替换所有相关回调才能显示 5 |

另一组比例菜单数据位于 `0x53DA3744`：数量 `+0x00` / `0x531CF298` 返回 4；标签 `+0x08` / `0x531D0CCC` 以第三参数作为索引；设置 `+0x18` / `0x531D2F70` 和选中 `+0x20` / `0x531D4898` 均读同一四字节顺序表；提交 `+0x28` / `0x531D8FFC` 会调用设置函数。第五项须覆盖这组相关入口，不能只修改主菜单。当前尚未证实它在机身上对应哪个可见操作位置。

`firmware/xpan_core.c` 现将项目菜单顺序固定为 `3:2 / 4:3 / 1:1 / 16:9 / XPAN`，允许 XPAN 与三种焦距裁切组合。选择 XPAN 时原生画面比例投影为 3:2，**保留当前原生焦距裁切及其倍率**；项目独立状态决定上下 65:24 窗口。退出或关闭项目覆盖时恢复进入前的普通比例。`firmware/xpan_menu_bridge.c` 增加离线菜单分派约定：原四项只调用原回调，第五项标签由独立回调提供，选择第五项仅将原生菜单索引 0 交给原回调；原回调失败时不提交逻辑状态。它尚未绑定两处菜单各自的实际 ABI，也没有写入相机属性或显示原生图标。

拍摄计划取本次拍摄已确认的焦距裁切后 3:2 源宽高，从该源取全宽、居中的 65:24 窗口，同时记录对应焦距倍率。预览与 DNG 使用同一窗口；DNG ABI 包装只有在当次倍率和合法原生 3:2 ID 都与计划一致时才使用 XPAN 参数，否则委托原函数。JPEG 422 描述适配仍只接受已验证格式与缓冲范围。实际源尺寸、各焦距裁切的 RAW 起点、取景链和压缩后文件仍须在原生调用上下文核实。

[`check_xpan_core.py`](../tools/check_xpan_core.py) 检查三裁切×四普通比例、第五项菜单顺序和选中、三裁切×XPAN 投影、退出恢复、每张照片计划、DNG 倍率匹配、像素源及缓冲恢复。ARMv7 硬浮点可重定位对象通过编译且无未解析符号；对象仍不是可直接导入相机的安装包。

`[宽16、高8、起点2]` 的离线例子给出 6192×2288、顶部 920；投影到 720×480 预览得到 `[0,106,720,267]`。对齐参数仅是电脑端示例，不能作为已确认的机内 JPEG/RAW 参数。项目另提供 [`xpan_aspect_icon.svg`](../examples/xpan_aspect_icon.svg) 作为 XPAN 宽幅图标矢量草稿；它不是原厂 `ICONBIN` 格式。要在机身实现，还须接通两个比例入口和轮换、状态/图标、实时预览、JPEG/DNG、持久化，以及可卸载的原生装载器。SD 卡自动诊断脚本已移除，下一轮机身读取会合并验证项目所需原生地址，避免为单一线索反复插拔卡。

### 原裁切菜单的保留依据

裁切行 `0x53D9FDE8` 的标签、选中、设置、数量回调依次为 `0x531BE354`、`0x531BB288`、`0x531BAFA0`、`0x531BA154`，数量返回 3。另有 `0x531CF2A0` / `0x531D2FA8` 形成的第二条裁切菜单路径。倍率表 `0x53DBAC10` 的第四个 word 是整数 30，不是第四个浮点倍率；当前方案不修改该表或原三档数量。[`audit_crop_menu.py`](../tools/audit_crop_menu.py) 固定核对这两条原生路径。

### 拍摄窗口、DNG 接口与实际像素源适配

`firmware/xpan_capture.c` 新增每张照片的固定窗口计划。菜单状态在拍摄开始时形成快照，之后切换菜单不会改变这一张照片的窗口。它验证完整 RAW 范围、中心位置与外部提供的对齐要求，预览与 DNG 从同一计划取值；相机上的状态锁和生命周期尚未接入。

Kb636 调用点 `0x5387E3D0` 及 `0x5387E3F0..0x5387E3FC` 的存储确认原生参数块四个半字字段：宽 `+0x18`、高 `+0x1A`、左 `+0x1C`、顶 `+0x1E`。适配只改这些字段，保留完整 RAW 数据尺寸和其他内容；它不是 DNG/TIFF 文件编辑器。`firmware/xpan_dng_bridge.c` 按叶函数的 ARM 硬浮点 ABI 实现包装：四个输出指针位于 `r0..r3`，倍率在 `s0`，比例 ID 在栈上。未就绪或上下文不匹配时调用原函数。安装器必须提供未修改的原函数或经过核对的跳板；禁止直接跳到已被同一包装覆盖的地址，否则会递归。尚未实现跳板或安装器。

实际像素路径来自 `ProcessModule/src/BackResizeMacroProcess.cpp`。`0x536FB040` 复制主图源描述后，按中心差值×行跨度调整两路 YCbCr 地址。描述复制函数 `0x538D336C` 确认地址在 `+4/+8`，宽高在 `+0x10/+0x12`，行跨度在 `+0x14`。原生转换函数的断言进一步确认格式 1 为 422、格式 2 为 420。

据此新增 `gr4_xpan_capture_ycbcr422_source`：只接受格式 1、与计划一致的完整源图、独立提供的两路分配长度；选择中心像素行并保留行跨度、其他描述字段。检查均通过后才更新描述，拒绝不匹配格式、短缓冲、地址溢出和重复应用。它不直接访问像素或相机内存。**运行时主图源格式及分配边界仍未读回，不能把静态格式定义当成当前缓冲值。**

`0x536FB0DC` 另调用原生尺寸计算器并写目标宽高 `+0x10/+0x12`。只改源窗口而不配套改目标尺寸会缩放变形；只改目标尺寸则可能缩小完整原图。真实接入还需核实源/目标配置、缩略图与回放、缓存操作和编码器的对齐要求。

`tools/audit_xpan_capture_paths.py` 固定核对上述样本字节及源文件身份。扩展的 `tools/check_xpan_core.py` 通过宿主检查及 ARMv7/VFPv3 硬浮点编译，无未解析符号；测试用两路独立合成像素验证 260×176 源图（行跨度 272）选择第 40 至 135 行，得到准确的 260×96 中心画幅。6192×4128 示例采用 Kb636 起点，得到 DNG 字段 `[6192,2288,54,978]`，RAW 容器尺寸仅为测试输入。

`firmware/xpan_module.c` 聚合这些源文件；输出为可重定位 ARM 对象，**不是相机安装包**。DNG 包装的就绪状态默认为 0，完整预览/JPEG 链、原生同步、恢复与代码装载验证之前不得启用。图标、持久化和实时视口还未实现。本轮没有修改 SD 卡、机内内存、资源、固件或版本号。

用户要求可恢复后，新增 `firmware/xpan_undo.c`：DNG 参数及 422 源描述在修改前记录原值，恢复前逐项核对仍是本模块写入的值；遇到冲突、错误目标或短缓冲不做写入。另加入 `gr4_xpan_dng_disable()`，停用覆盖时保留原函数委托。电脑端恢复检查与 ARM 编译通过；原生挂钩恢复、缓存同步、调用排空和外部冷启动恢复仍未实测，不能把缓冲恢复检查当成机身恢复证明。

### 升级包离线重建进度

`tools/repack_firmware_experimental.py` 现可把修改后的等长解码载荷重封装为 GR IV 更新容器。它保留未变更的压缩帧，把变更帧写成原格式支持的原样帧；随后重新计算流长度、解码长度和整文件 32 位加法校验。每次输出都再次解包并逐字节比对目标载荷。

对本地 1.11 包的两项离线测试：

- **零改动往返**：输出 SHA-256 与原包完全相同，均为 `a2f664dfca034059eb0fd6e18ab08684c326b4a034d85c164dad7e1ec9b5655f`。
- **单字节试验**：只改解码载荷里一个测试文字字节，重封装替换了一个压缩帧；再次解包与目标载荷逐字节一致，整文件加法校验为零。测试输出仅保存在 `/private/tmp`，未发送给相机。

这些检查**不证明**相机接受改动包。升级器可能还有机型、版本、内部块校验或签名验证；流长度变化时补齐字节如何被升级器处理也未实机确认。当前没有经过验证的 XPAN 功能补丁，因此不应把试验重封装文件当作相机升级包。

版本门槛已单独追踪到“候选组件版本低于当前版本才拒绝”的分支，并完成只改包头和 GR IV 包尾版本副本的离线工具；见[升级版本检查分析](gr4-update-version-check.md)。这并未证实相同版本可以通过整个升级流程，也未得到可刷入的 XPAN 固件。

继续反汇编还确认：`0x5380D1D0` 的四项画面比例分支只写入 Makernote 元数据；修改上限不能得到 65:24 像素范围。静态图生成、预览、DNG 标签、图标和持久化路径都需要接纳独立 XPAN 状态。调试文本虽出现 `CropMag` 第 3 项 `3.125`，实际用户裁切倍率表（`0x53DBAC10`）只有三项，不能把这条文本当作可直接复用的 XPAN 空档。

当前研究阶段不能产出可安装的 XPAN 固件，也不能通过现有 TTL 文件复制脚本实现实时取景和拍摄管线改动。下一步应先从 `ChangeCrop`、`ChangeAspectRatio`、`LvChangeCrop`、JPEG/DNG 裁切窗口和图标资源的交叉引用建立调用图，再核实可重打包和恢复路径。

## 不更新固件的路径

SD 卡入口的进一步核对见[SD 导入路径分析](xpan-sd-path.md)：Linux 会挂载卡，但启动配置没有从卡上自动执行程序；RTOS 的 TTL 脚本能运行，尚未证实能注册新画面比例或运行本机代码。

已验证的 SD 卡 TTL 启动脚本能复制资源文件，包括关机 JPEG；第二阶段返回值探针还确认它能调用本机工程 shell。尚未证明它能把新画面比例注册到菜单、修改 LCD 图层或安全加载运行时代码。第三阶段 Linux 标记未生成，Linux 桥接仍待确认，因此还不能交付开机后注入的 XPAN 模式。固件内的 `ICONBIN` 是独立二进制区段（本样本位于文件偏移 `0x2E93AE0`），并非已经找到可用 `filecopy` 替换的独立图标文件。

可以不改相机软件而分两步接近目标：

1. 相机以 3:2 全画幅拍摄；在后屏覆盖可移除的 65:24 构图线/遮罩，或通过 USB-C DisplayPort Alt Mode 把取景画面送到外部采集设备，在外部屏幕叠加遮罩与 XPAN 指示。`examples/xpan_3x2_overlay.svg` 是透明中心、上下遮罩和 XPAN 标签的 720×480 矢量叠加层，须对齐**实际 3:2 取景区域**；不能直接拉伸到整个 16:9 输出信号。理光[GR IV 官方 FAQ](https://www.ricoh-imaging.co.jp/english/support/qa/gr-4/)说明外部显示时机身 LCD 关闭，因此后者无法同时改变机身屏幕。理光[GR WORLD FAQ](https://www.ricoh-imaging.co.jp/english/support/qa/gr-world/)说明该手机应用没有 Live View。
2. 将拍摄的 JPEG 复制到电脑，用 `tools/xpan_reference.js` 生成中心 65:24 裁切。此时成片是电脑上的新文件，机内原片与回放仍为原比例。该工具尚不处理 DNG、批量导入或自动监控文件夹。

这两步可以实现构图参考与最终 JPEG 画幅，但不是“机内新增 XPAN 菜单/图标/保存格式”。若要求三者都在机内生效，需要可靠的运行时代码注入路径及对拍摄管线的完整修改，或者固件级修改；目前两者均未验证。
